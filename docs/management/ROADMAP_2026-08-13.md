## 2. New Risks Identified by ROTHER-AUDIT (RISK-023 … RISK-027)

### RISK-023 — Review Acquisition Is Non-Functional (Auth-Gated Root Cause)
- **Severity:** Critical | **Status:** Open — root cause identified, fix deferred (backend)
- **Finding:** `reviews_tab_button` activation scored 0/12 across all parser tiers; all acquisition tiers return 0 reviews unauthenticated. Prior audits blamed "selector drift"; the actual root cause is **Google Maps requires an authenticated session** to surface the reviews tab. The scraper runs unauthenticated headless Chromium.
- **Proposal (P1):** Acquire reviews via the **Google Places API** (Places Details `reviews` field) using an API key, instead of DOM scraping the reviews tab. Places API returns up to 5 most-relevant reviews per place, no pagination (`next_page_token` not supported for reviews). This removes the auth-gating blocker entirely for the review-acquisition use case.
- **Rother construct:** Muda (wasted acquisition effort) + bottleneck at the reviews-tab gate.
- **Falsifiable claim:** "A Places API call for a real `place_id` returns ≥1 review." Testable with one API call.

### RISK-024 — Multi-Category / Multi-Business Feature Unsupported
- **Severity:** High | **Status:** Open — 3 independent backend blockers
- **Finding:** `listings.json` has no `category` dimension; `src/lib/gbp/types.ts` `ListingsConfig` has no category field; `discovery/` only contains a `validate_listing.py` reachability pre-check (no category/business discovery backend); acquisition is broken (RISK-023). Three independent blockers must all be solved.
- **Proposal (P2):** Add `category` + `business` dimensions to `ListingsConfig`; build a discovery backend that enumerates categories/businesses per place; depends on RISK-023 acquisition fix.
- **Falsifiable claim:** "Given a place with 3 categories, the dashboard returns 3 category-scoped result sets." Blocked until acquisition works.

### RISK-025 — Viability Evidence Gap (Tests/CI Always Pass)
- **Severity:** High | **Status:** Open
- **Finding:** No CI workflow runs the test suites. `golden-datasets/` is empty (`.gitkeep` only). `gbp-monitor/tests/verify_baseline.py:311` accepts a result of `0` or `1` — a guaranteed pass. `run_all.py:1646` `sys.exit(0)` in live mode makes GitHub Actions always green even when scraping fails. The system cannot demonstrate it works.
- **Proposal (P5):** Add CI that runs `pytest` + `vitest`; require non-empty golden datasets; change `verify_baseline.py` to require a real threshold; make live runs exit non-zero on failure.
- **Falsifiable claim:** "CI fails when `golden-datasets/` is empty or baseline score < threshold."

### RISK-026 — Tauri Plan Data-Story Is Inaccurate (No SQLite)
- **Severity:** Medium | **Status:** Documented (correction added to `TAURI_CONVERSION_PLAN.md`)
- **Finding:** `TAURI_CONVERSION_PLAN.md` repeatedly states the app uses **SQLite** (lines 20, 56, 106, 125–127) and that Prisma "loads against the bundled SQLite file." In reality the dashboard data layer is **JSON-file based** (`src/lib/gbp/server-data.ts` reads `snapshots/`, `reviews_new/`, `run_summary.json`). Prisma/`lib/db.ts`/`prisma/schema.prisma` are **dead code** (TD-M03). There is no SQLite dependency in the live data path.
- **Impact:** The Tauri bundle/architecture plan over-provisions (bundles a Node sidecar + Prisma engines for a DB that isn't used). The correct offline story is: Next standalone + JSON files on disk + optional Python scraper sidecar.
- **Proposal (P6):** Treat JSON files as the canonical offline store; remove dead Prisma from the bundle budget; correct the plan doc (done — see §5).
- **Falsifiable claim:** "No code path in `src/lib/gbp/server-data.ts` imports `@prisma/client`." Verified true.

### RISK-027 — CI Reports Success on Failed Live Runs
- **Severity:** Medium | **Status:** Open
- **Finding:** `run_all.py:1646` calls `sys.exit(0)` in live mode, so GitHub Actions shows green even when `failed > 0`. Combined with RISK-025, the project has no honest signal of whether acquisition works.
- **Proposal (P5 cont.):** In live mode, `sys.exit(1 if report["failed"] > 0 else 0)`.
- **Falsifiable claim:** "A live run with 1 failed listing exits non-zero." Backend change; deferred per "minimal backend" constraint but spec provided.

  if not parsed_dicts and old:
