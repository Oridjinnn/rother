## B. Phase 2 — Researched Proposals (NEW high/med + feature decisions)

Each: **Problem → Sourced research → Proposed fix → Maps to → Fixture → Blast radius.** Status = HYPOTHESIS.

### B1. T1 — Tauri CSP blocks the app's own API origin (refined, HIGH)
- **Problem:** `tauri.conf.json:26` production `connect-src` = `ipc: http://ipc.localhost` only. The Node sidecar serves the app on `http://127.0.0.1:4632` (`main.rs:30,82`); the webview's own `fetch('/api/...')` targets that origin and is CSP-blocked → silent desktop data failure.
- **Research:** S11/S12 — `connect-src` must include every fetch target; same-origin is not implicit. Run-1 reported `csp:null` (disabled); fresh read shows CSP is now SET but incomplete.
- **Fix:** add `http://127.0.0.1:4632` (and/or `'self'`) to `connect-src` in production CSP; keep `devCsp` as-is for HMR. Add `freezePrototype: true`.
- **Maps to:** `src-tauri/tauri.conf.json:26`.
- **Fixture:** `tauri build` + load → assert webview `fetch('/api/overview')` succeeds and no CSP-violation console errors for bundled assets.
- **Blast radius:** 1 file. **Confidence: CONVERGED.**

### B2. E3 — `selector_tracker` false-positive (HIGH)
- **Problem:** `selector_tracker.py:131-141` folds `expected_missing_count` into `effective_found` and reports `status="healthy"` when all entries are `expected_missing`. A selector that is *present but should be absent* is indistinguishable from one *truly absent* → "healthy" either way.
- **Research:** internal (E3 depth). Root: the tracker conflates "absence expected" with "absence achieved."
- **Fix:** track a separate `unexpected_present` counter; if `found_count > 0` while `expected_missing` is set for those same entries, mark `status="broken"` (not healthy). Never count `expected_missing` toward `effective_found`.
- **Maps to:** `gbp-monitor/harness/selector_tracker.py:131-141`.
- **Fixture:** unit test feeding one entry `found=True, expected_missing=True` → asserts `status != "healthy"`.
- **Blast radius:** 1 file. **Confidence: CONVERGED.**

### B3. D7 — Active business has no `branches` → empty panels via new onboarding (HIGH)
- **Problem:** `user-business.json` (written by `scrape/trigger/route.ts:44-48`) carries no `branches`; `readActiveBusinessBranches()` (`server-data.ts:469-474`) falls back to seed while `readListings()` returns `[]` once a business is active (`:101-104`) → owner lands on empty branch/competitor panels even though seed data exists.
- **Research:** internal; compounds D4 (silent empty dashboard) through the new Run-gate path.
- **Fix:** when an active user business exists but has no branches, `readActiveBusinessBranches()` should surface an explicit "no branches configured yet" state (not silently seed), and the onboarding/Run flow should persist the chosen business's branches (from geocode/branch step) into `user-business.json` so the panels have data.
- **Maps to:** `server-data.ts:469-474`; `scrape/trigger/route.ts:44-48`; `onboarding.tsx`.
- **Fixture:** test with an active business lacking branches → UI shows explicit empty-state, never seed-masked data.
- **Blast radius:** `server-data.ts` + onboarding + 2 UI empty-states. **Confidence: CONVERGED (mechanism) / PARTIAL (onboarding data capture).**

### B4. C5 — `API_KEY` drift: auth gate silently open (MED)
- **Problem:** `middleware.ts:24,79` reads `API_KEY`; if unset, all requests pass. It is defined in **no** env file, so the instance ships unprotected with no documented key.
- **Fix:** document `API_KEY` in `.env.example` with a generated default for local dev; add a startup log line when auth is disabled; consider failing closed in production builds.
- **Maps to:** `src/middleware.ts:24,79`; `.env.example`.
- **Fixture:** middleware test with `API_KEY` unset in prod-mode → asserts 401 on mutating `/api` calls.
- **Confidence: CONVERGED.**
